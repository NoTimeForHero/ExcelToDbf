# Выходной DBF

Конвертер использует поставляемую SocialExplorer.FastDBF и пишет dBASE III без memo (первый байт заголовка 0x03). Один объект, возвращённый `write`, соответствует одной записи. `null` пропускает строку Excel; `stop()` завершает строки.

## Схема

`dbfFields` задаёт порядок полей. Имена и ключи возвращённой записи должны совпадать с учётом регистра. Отсутствующий ключ оставляет поле пустым. Посторонний ключ записи не создаёт новое поле.

| Тип в config.js | Тип DBF | Длина | Примечание |
| --- | --- | --- | --- |
| `string` или не указан | C | Обязательна, 1..254 байта | Строковое преобразование значения |
| `number` | N | По умолчанию `10,2`, ширина до 20 | Вся ширина включает знак и десятичную точку; второй параметр — знаки после точки |
| `date` | D | 8, можно не указывать | В файле yyyyMMdd |

Имя поля: 1..10 ASCII-символов, первая буква или `_`, далее буквы, цифры или `_`. Дубли без учёта регистра запрещены. Для числа точность 0..15; для ненулевой точности должны оставаться минимум позиция целой части и точка. `length: '10,2'` означает десять позиций целиком, а не десять цифр плюс дробная часть.

Пример:

```javascript
dbfFields: [
    { name: 'ID', length: '8' },
    { name: 'FIO', length: '60' },
    { name: 'SUMMA', type: 'number', length: '10,2' },
    { name: 'DATEOPL', type: 'date' }
]
```

## Преобразования и потери

Кодировка выбирается `app.settings.system.outputEncoding`, например 866 или 1251. Передавай её явно и согласуй с CRM. В текущем формате FastDBF байт language driver может оставаться 0; при чтении используется кодировка из конфига. Не определяй её только по заголовку.

Длины строк считаются в выходных байтах. Библиотека разрешает обрезание строк; CLI выдаёт `STRING_TRUNCATED`, а при непредставимом символе — `ENCODING_LOSS`. `--strict` останавливает обработку вместо принятия потери. Для многобайтной кодировки проверка чтением также обнаруживает повреждённую последовательность после обрезания.

Обрезание считается для каждой записи и каждого поля отдельно, поэтому предупреждений может быть больше, чем записей: на реестре из нескольких сотен строк адреса обрезаются два-три десятка раз. Полное число даёт `dataWarningCount`, а сам список в `warnings` ограничен 200 элементами. Значение в `dbf.sample` у `validate` уже обрезано, `conversion.sample` показывает то, что вернул `write`.

Число перед записью преобразуется в строку, запятая заменяется точкой. Допускаются знак минус, цифры и необязательная дробная часть. Пробелы, валюта, экспонента и пустое переданное значение не являются допустимыми числами. Неверный формат даёт `INVALID_NUMBER`, непомещающееся число — `NUMBER_OVERFLOW`. Избыточная дробная точность даёт `NUMBER_PRECISION_LOSS`; результат обычного режима зависит от форматирования библиотеки и виден в прочитанном DBF. Для оплаты предпочтительны явная нормализация и строгая проверка.

Дата распознаётся существующим преобразователем из подстроки с точками: `dd.MM.yyyy` или `yyyy.MM.dd`. В строке может быть время. Пустое значение записывается пустым. Нераспознанная или календарно недопустимая дата даёт предупреждение `INVALID_DATE` и пустое поле; некоторые некорректные формы даты вызывают ошибку преобразования. В `--strict` потеря даты запрещена. Не рассчитывай на автоматический разбор ISO, двухзначного года и произвольного локального формата.

После закрытия DBF CLI независимо проверяет заголовок, типы и длины полей, число записей, каждое числовое поле и дату, декодирование строк. В JSON даты представлены как `yyyy-MM-dd`, числа как JSON number, пустые числовые и календарные поля как null. Образец ограничен первыми пятью записями; суммы считаются по всему DBF.

## Сверка с историческими файлами

При сравнении с DBF, созданным прежней версией программы, отделяй служебный заголовок от данных. Область записей (`rlen * nrec` байт после заголовка) должна совпадать полностью; в шапке законно различаются дата создания в байтах 1–3 и байт language driver в позиции 29 (например, `0` у новой записи против `0x26` у старой). Сравнение только первых записей или только сумм недостаточно: сдвиг строки, её потеря или обрезание в середине файла так не видны.

Если рядом с исходным документом исторического DBF нет, это может быть не пропуском, а свидетельством того, что старая программа отклоняла документ. Такое расхождение объясняй проверкой правил, а не считай ошибкой переноса.

## Что считать подтверждением

Успешная запись доказывает, что документ прошёл выбранные JS-правила и технические проверки DBF. Правильность выбора счёта, назначения платежа, сумм и других бизнес-полей дополнительно задаётся ожиданиями manifest и контрольными условиями `afterWrite`.

Совместимость конкретной CRM должна подтверждаться её требованиями, утверждёнными файлами или импортом. Входящие в поставку примеры фиксируют поведение проекта и не являются универсальным контрактом всех CRM.
