# JS API правил, версия 1

Правила исполняются Jint 3.0.0-beta-2042 внутри .NET Framework 4.7.2. Используй обычные функции, объекты, массивы, строки и проверенные примеры. Доступны `const`, `let` и шаблонные строки, использованные в конфиге поставки. Современный JavaScript целиком не гарантируется. Node.js, браузерный DOM, `require`, `fetch`, импорт внешних модулей и сетевые API не предоставляются.

## Структура конфигурации

Перед загрузкой приложение создаёт `app = {}`. Конфиг задаёт:

```javascript
app.settings = {
    system: {
        outputEncoding: 866,
        bufferSize: 200,
        fastSearch: false,
        noFormIsError: false,
        extraWarning: 'Не все файлы сконвертированы'
    },
    header: { title: 'Название фирмы', status: '' },
    extensions: ['*.xls', '*.xlsx', '*.xml']
};
app.getOutputFilename = function(file) { return translit(nospace(file)) + '.dbf'; };
app.forms = [ /* объекты форм */ ];
```

`outputEncoding` — номер кодовой страницы .NET, обычно 866 или 1251. `bufferSize` — от 1 до 100000. `fastSearch` останавливает проверку формы после первого неудачного assert, а перебор форм — после первого совпадения. Даже при `false` выбирается первая подходящая форма, но выполняются правила **всех** форм: исключение в правилах любой из них срывает документ, даже если более ранняя форма уже совпала. При `true` оставшиеся формы не проверяются. Для конфига с несколькими формами это различие определяет, получишь ли ты полную диагностику несовпадений или устойчивость к ошибке в редкой форме.

`header`, `extensions`, `noFormIsError`, `extraWarning` используются GUI. Явная команда CLI обрабатывает переданный файл независимо от масок `extensions`, а отсутствие формы всегда даёт код 1. Старый блок `logging` из примеров принимается молча и не даёт предупреждения, но на CLI не влияет: логи идут в stderr.

Неподдерживаемые свойства возвращаются с предупреждением `UNSUPPORTED_PROPERTY`, включая опечатки в settings и dbfFields. В строгой проверке предупреждения запрещены. Для собственных вспомогательных данных используй переменные и context, а не произвольные свойства app и описаний полей.

## Объект формы

```javascript
{
    name: 'Уникальное имя формы',
    settings: { startY: 8, endX: 7 },
    rules: function() { assert(cell(2, 2), 'Идентификатор документа'); },
    dbfFields: [
        { name: 'ID', length: '8' },
        { name: 'SUMMA', type: 'number', length: '10,2' },
        { name: 'DATEOPL', type: 'date' }
    ],
    beforeWrite: function() { context.sum = 0; },
    write: function(line) {
        if (includes(line[2], 'ИТОГО')) return stop();
        if (!line[2]) return null;
        context.sum += parseFloat(line[5]) || 0;
        return { ID: line[2], SUMMA: line[5], DATEOPL: line[6] };
    },
    afterWrite: function() { log('Сумма: ' + context.sum); }
}
```

`name` обязателен и уникален. `rules` и `write` — обязательные функции; `beforeWrite` и `afterWrite` необязательны. `dbfFields` не должен быть пустым. Схема полей описана в [DBF](dbf-format.md).

`startY` — первая строка данных от 1 до 1048576; для плавающего заголовка разрешён -1. `endX` — последний включённый столбец, от 1 до 16384. Чтение всегда начинается со столбца A. При -1 правило обязано определить допустимый `context.startY`.

## Порядок выполнения и состояние

1. Для первого листа проверяются формы в порядке `app.forms`.
2. Каждая форма получает новый `context`; выполняется `rules`.
3. Форма подходит, если выполнен хотя бы один `assert` и все выполненные assertions успешны. Возвращаемое значение `rules` не определяет совпадение.
4. Сохраняется контекст первой подходящей формы. Остальные формы его не меняют. При следующем документе контекст создаётся заново.
5. Определяется начало данных: `context.startY`, если задан, иначе `settings.startY`.
6. Выполняются `beforeWrite`, затем `write(line)` для каждой строки до конца используемого диапазона или `stop()`.
7. После нормального завершения строк, включая `stop()`, выполняется `afterWrite`. Если `write` выбросил ошибку, заключительный хук не выполняется.

При ошибке `beforeWrite`, `write`, записи DBF или `afterWrite` конвертация неуспешна. `stop()` предназначен только для `write`. `context.startY` устанавливается в `rules`: изменение начала данных в `beforeWrite` уже не влияет на чтение. Изменение глобальных переменных и других форм создаёт неявные зависимости; храни промежуточное состояние в `context`.

## Строки реальных реестров

Выгрузки из учётных систем обычно сложнее одной шапки и одного итога:

- лист печатается страницами, поэтому шапка (`№ п/п`) и подпись (`Документ подготовил: …`) повторяются внутри одного листа по многу раз, а между блоками идут пустые строки;
- итоговая строка (`Итого:`) стоит до подписи и до следующей страницы;
- часть столбцов шаблона пуста во всех документах (например, `ФИО абонента`), а в другой раскладке того же отчёта те же данные сдвинуты на один столбец.

Из этого следуют требования к правилам: условия пропуска должны быть идемпотентны и проверяться для каждой строки; `stop()` уместен только там, где после итога действительно нет данных; форма должна отличаться assert по конкретным ячейкам шапки, а не по «похожести» документа.

## Ячейки, диапазоны и строки

| API | Поведение |
| --- | --- |
| `cell(y, x)` | Ячейка с координатами от 1: объект с `Y`, `X`, `Value`. `Value` — строка или null для пустого значения. Ошибка чтения является ошибкой обработки |
| `findRange(startY, endY, startX, endX, expected)` | Точное сравнение со строкой в прямоугольнике, обе границы включены; поиск по строкам сверху вниз, слева направо. Возвращает Cell или null |
| `assert(actual, expected)` | `actual` — строка или Cell, `expected` — только строка или JS RegExp. Возвращает bool и сохраняет результат проверки. Другой тип ожидания (например, `true`) — ошибка `RULES_FAILED` с сообщением `Unknown assert 'Expect' type` |
| `context` | Обычный JS-объект выбранной формы, доступный в rules, хуках и write |
| `write(line)` | Массив значений Excel: `line[0]` пустой, `line[1]` — A, `line[endX]` доступен. Верни объект с DBF-полями либо null |
| `stop()` | Завершает обработку строк специальным исключением; обычно используется `return stop()` |

Имена свойств Cell в примерах следует писать как `Value`, `Y`, `X`. Старые примеры могут использовать другую капитализацию; не принимай это за общий контракт всех объектов.

Значения `line` читаются через `Range.Value`, поэтому могут быть числами, строками, датами или null. `cell().Value` получается строковым преобразованием .NET. Формат может зависеть от типа и локали. Не путай типизированное число с текстом, содержащим пробелы, валюту или запятую; преобразуй текст явно и проверяй результат. Не превращай ошибку разбора оплаты в ноль без бизнес-основания.

Типизированная дата приходит объектом с `getFullYear()` и `getMonth()`, текстовая — строкой; к обоим вариантам нельзя применять одно строковое регулярное выражение. Для чисел помни, что `String(v)` не повторяет .NET `ToString()`: целое `double` печатается без дробной части, дробное — с точкой вместо запятой (в ru-RU у .NET там запятая), а значения от `1e15` .NET выводит в экспоненциальной записи (`4,08028109E+19`) там, где JS печатает все цифры. Если старое правило опиралось на строковое представление числа, воспроизведи его явно, иначе в поле попадёт другое значение.

Плавающий заголовок:

```javascript
rules: function() {
    if (!assert(cell(2, 2), 'Новая форма')) return;
    const header = findRange(4, 100, 2, 2, '№');
    if (!header) { assert('не найден', '№'); return; }
    context.startY = header.Y + 1;
    assert(cell(header.Y, 3), 'ФИО');
    assert(cell(header.Y, 5), 'Сумма');
}
```

## Базовые функции

| Функция | Аргументы и результат |
| --- | --- |
| `match(input, pattern)` | Строковый шаблон .NET Regex; bool. Для null возвращает false |
| `matches(input, pattern)` | Массив значений групп первого .NET Regex.Match: индекс 0 — полное совпадение, далее группы. Для null возвращает []; отсутствие совпадения обычно даёт пустую группу 0 |
| `includes(input, search)` | Поиск подстроки без учёта регистра через .NET ToLower. Null считается пустой строкой; пустая искомая строка находится |
| `nospace(input, replacement)` | Заменяет последовательности пробельных символов `\s+`; replacement по умолчанию пустая строка |
| `translit(input, maxSafe)` | Русская транслитерация, удаление недопустимых символов имени файла. По умолчанию maxSafe=true, также удаляются апострофы, кавычки и обратные кавычки |
| `afterRegEx(input, regex, index)` | Устаревшая функция: Regex.Split, а не массив групп Match; возвращает элемент split с индексом (по умолчанию 1) либо null. Для новых правил предпочитай matches |
| `log(message)` | Сообщение в лог; в CLI — stderr, JSON stdout остаётся чистым |
| `error(message)` | Прерывает обработку с сообщением об ошибке |

В `assert(cell(6, 2), /на \d{2}\.\d{2}\.\d{4}/)` передаётся JS RegExp, который хост преобразует для сравнения. В `matches(value, '(\\d+)')` передаётся строковый шаблон .NET; обратный слеш внутри JS-строки нужно удваивать. Не рассчитывай на полное совпадение синтаксиса и флагов JS RegExp и .NET Regex.

Флаг `i` хост учитывает: `assert(cell(6, 17), /^Сумма Итого, руб/i)` срабатывает и на `СУММА ИТОГО, РУБ.`. Это и нужно для старого `validate="regex"`, где сравнение шло без учёта регистра. Инлайновые опции вида `(?i)` работают только в строковых шаблонах `match` и `matches`; передать результат `match(...)` в `assert` нельзя — ожидание должно быть строкой или RegExp.

В старом хосте есть заглушка `test(value)`, всегда возвращающая null; для правил и проверок она не используется. Функции `matched` из прежних комментариев нет.

## Ошибки из правил

`error(message)` прерывает обработку; код и `stage` определяются местом вызова:

| Где вызван `error` | `code` | `stage` |
| --- | --- | --- |
| `rules` | `RULES_FAILED` | `rules` |
| `beforeWrite` | `CONVERSION_FAILED` | `beforeWrite` |
| `write` | `CONVERSION_FAILED` | `write` (с `sourceRow`) |
| `afterWrite` | `CONVERSION_FAILED` | `afterWrite` |
| `app.getOutputFilename` | `OUTPUT_NAME_FAILED` | `output-name` |

Текст сообщения попадает в `message` ошибки, поэтому формулировки стоит делать понятными для оператора. Такие ошибки — ожидаемая часть правил: в manifest для них задают `expected.error.code` и `stage`.

## Имя выходного файла

`app.getOutputFilename(file)` получает исходное имя без расширения и возвращает строку. Относительный результат считается от директории входного файла. В функции доступны базовые функции и:

- `file` — исходное имя без расширения;
- `dirCount` — число сегментов полного исходного пути;
- `dir(index)` — сегмент от конца пути: `dir(0)` сейчас включает имя входного файла с расширением, `dir(1)` — его родительский каталог; за пределами верхней границы возвращается null. Используй неотрицательные индексы.

Это сохранённая семантика текущего PathHelper. Явный `convert --output` задаёт целевой путь независимо от этой функции. `validate` показывает вычисленный путь, но пишет только временный результат.

## Совместимость с прежней реализацией

Исправлены пропуск последнего столбца, границы блоков, подсчёт последней строки UsedRange и номер строки в ошибке. Индексы имеющихся столбцов сохранены. Изоляция `context` теперь соответствует выбранной форме; не полагайся на значения, записанные другой формой. Пустые `rules` больше не распознают любой файл.

Ранее эти особенности могли скрывать ошибки правил. После переноса существующего конфига запускай его регрессионный набор. XML-документация старых выпусков к текущему JS API не относится.
