# Сборка и проверка CLI

Проекты остаются на .NET Framework: Engine, App, Cli и UnitTests — 4.7.2, CSV_Converter — 3.5. Нужны Visual Studio/MSBuild с соответствующими targeting packs, восстановленные пакеты из `packages.config` и установленный Excel для интеграционных проверок.

В Developer PowerShell Visual Studio:

```powershell
msbuild .\ExcelToDbf.sln /t:Build /p:Configuration=Debug
vstest.console.exe .\UnitTests\bin\Debug\UnitTests.dll
.\tests\cli-smoke.ps1
.\tests\package-smoke.ps1 -Configuration Release
```

`cli-smoke.ps1 -FoundationOnly` проверяет базовые команды и тайм-аут JS. Полный набор дополнительно запускает настоящий Excel, CSV, преобразование и чтение DBF, ошибки, строгий режим, перезапись, тайм-аут после записи, сохранность другого Excel и manifest-регрессии. Для другой директории сборки можно передать `-Cli`, `-Config`, `-TestData`; этот скрипт рассчитан на примеры проекта.

Проверены PowerShell 7 и Windows PowerShell 5.1. В тестовых скриптах явно настроены UTF-8 и обработка native stderr для 5.1; пользовательские вызовы описаны в [справочнике CLI](../distribution/docs/cli.md).

`package-smoke.ps1` собирает App, распаковывает Release-архив в изолированную директорию с пробелами и Unicode в пути, проверяет его состав и запускает проверки оттуда. Для проверок отдельно добавляются примерный конфиг и TestData. Сценарий не требует исходников для исполнения CLI, не меняет локальный конфиг фирмы и проверяет относительные ссылки документации. Артефакты остаются в игнорируемой `artifacts` для разбора.

GUI проверяется пользователем по [отдельному списку](gui-manual-checks.md). CLI-проверки не являются подтверждением визуальной работы GUI.

## Структура

- `Engine` — общие модели, Excel/JS/DBF и `ConversionPipeline` без окон и ViewModel.
- `App` — прежний GUI и адаптер прогресса; его `ConvertService` вызывает общий цикл на STA-потоке.
- `Cli` — аргументы, JSON DTO, команды, отдельный рабочий процесс и контроль времени/принадлежности ресурсов.
- `Packaging/Distribution.targets` — копирование инструкций, примеров и тестовых данных, инициализация конфига при его отсутствии.
- `distribution` — исходники документации для готовой поставки; не путать её `AGENTS.md` с инструкциями разработки репозитория.
- `App/TestData/cases.json` — версионируемые ожидания примеров; собственные фирмы используют свои manifest и входы.

Сборка App помещает зависимости в `App/bin/<Configuration>/DLL`. В Release CLI EXE, его PDB и конфигурация также находятся в `DLL`; в Debug CLI EXE остаётся рядом с GUI в корне. Конфиг по умолчанию и справка ищутся в корне поставки. Самостоятельная сборка Cli также получает документацию, конфиги и TestData, но её зависимости лежат рядом с CLI EXE. Полный GUI-дистрибутив — `App/bin/<Configuration>`.

Существующий `config.js` в выходной директории не заменяется сборкой независимо от времени изменения. Исходный `App/config.js` обновляет `config.example.js`; при отсутствии рабочего конфига он используется для первого запуска. Чтобы протестировать новый исходный пример после правки, явно передавайте `--config config.example.js`.

После сборки Release создаётся `App/bin/Release/App.zip` для обновления: в нём находятся `DLL`, `docs`, `AGENTS.md`, `ExcelToDbf.exe`, `ExcelToDbf.pdb` и `ExcelToDbf.exe.config`. Распакуйте архив поверх директории приложения; рабочий `config.js` в архив не входит и сохраняется. Это архив обновления, а не полная поставка: примерный конфиг и тестовые данные в него не включены.

Не добавляйте случайные DBF из `bin` в эталоны. Новый сценарий должен задавать независимые ожидаемые значения и проверять распознавание старых файлов. Служебная дата заголовка DBF не является бизнес-данными и не должна ломать сравнение.
