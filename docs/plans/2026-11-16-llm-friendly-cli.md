# План: работа LLM с правилами конвертации Excel → DBF

Дата: 16 ноября 2026 года.

Статус: CLI реализован и проверен. Документ сохраняет исходный план и критерии готовности; фактические изменения и проверки описаны в [заметках реализации](implementation-notes.md). По указанию пользователя ручные проверки GUI переданы ему: [список проверок](../gui-manual-checks.md).

## 1. Цель и принятые ограничения

Сделать готовую поставку конвертера пригодной для самостоятельной работы модели с новыми типами Excel-файлов. Модель должна уметь изучить документ, дополнить JS-правила, проверить распознавание и преобразование, обнаружить ошибки и подготовить рабочий конфиг.

Для этого ей не должны требоваться исходники C#, Visual Studio, пересборка приложения, рефлексия, ручной вызов внутренних методов или управление окнами приложения.

Зафиксированные условия:

- Среда выполнения — Windows с установленным Microsoft Excel. Чтение документов остаётся через Excel OLE/COM.
- Основной сценарий — готовая поставка без исходников.
- У каждой фирмы свой локальный `config.js`. Выбор конфигурации должен быть явным и отражаться в отчёте.
- Тестовые документы уже есть в `App\TestData`, их копии — в `App\bin\Debug\TestData`.
- Для исходного `App\config.js` и тестовых документов в проекте задано `CopyToOutputDirectory=PreserveNewest` («Копировать более позднюю версию»).
- Старые XML-конфиги части фирм будут переноситься отдельно, после выполнения текущей задачи.
- Существующий графический интерфейс должен продолжить работать.

Результат задачи — CLI, общий с GUI механизм конвертации, проверяемый контракт JS-правил, документация рядом с EXE и регрессионные сценарии, запускаемые из готовой поставки.

## 2. Что есть сейчас

Наблюдения по исходникам; это не результаты запуска конвертации:

| Область | Текущее состояние | Следствие для плана |
| --- | --- | --- |
| Запуск | `App.xaml.cs` вызывает `Core/Program.cs`, далее выполняются предзагрузка, автообновление и GUI | Нужна отдельная консольная точка входа |
| Конфигурация | `ConfigContext` читает `config.js` по относительному пути | Путь нужно передавать явно; определить поведение относительно EXE и рабочей директории |
| Правила | Jint исполняет `app.settings`, `app.forms`, `app.getOutputFilename` | Сохраняем существующий формат JS |
| Распознавание | `ExcelContext.SearchForm` собирает результаты `assert`, выбирает первую подходящую форму | Основа для команды `match` уже существует |
| Преобразование | `beforeWrite`, `write(line)`, `afterWrite` и общий `context` | Проверка должна проходить весь цикл, включая заключительный хук |
| Excel | `ExcelService` открывает первый лист и читает данные блоками | Нужно документировать выбор листа и фактическую семантику значений |
| DBF | `DBFService` создаёт файл, преобразует числа и даты, разрешает обрезание строк | Нужны проверка результата и диагностика потерь |
| Тесты | В `UnitTests` есть проверки JS и подстановка значений ячеек без Excel | Можно использовать для проверки контракта внутри проекта |
| Документация | `README.md` и `DOCUMENTATION.md` описывают прежний XML-формат | Нужен актуальный справочник для поставки |
| Упаковка | Post-build переносит DLL и вспомогательный CSV-конвертер в `DLL` | CLI нужно проверить в реальной структуре поставки |

В `App\bin\Debug\TestData` также найдены DBF от предыдущих запусков, включая файл для ошибочного примера. Само наличие DBF не подтверждает успешную конвертацию и не делает его эталоном. Эти файлы не перезаписывать при подготовке проверок.

## 3. Основное решение: CLI и общий механизм обработки

Основной интерфейс модели — отдельный консольный `ExcelToDbf.Cli.exe` рядом с существующим `ExcelToDbf.exe`. PowerShell используется для запуска команд, чтения JSON и работы с файлами.

Загрузка сборки из PowerShell не становится публичным интерфейсом: она привязывает сценарий к внутренним классам, регистрации зависимостей, потокам и освобождению COM-объектов.

Целевая связь компонентов:

```text
ExcelToDbf.exe     → GUI-адаптер ─┐
                                ├→ общий механизм обработки → Excel OLE / Jint / DBF
ExcelToDbf.Cli.exe → CLI-адаптер ─┘
```

Общий механизм принимает явные параметры запуска и возвращает обычные объекты результата. Он не показывает окна и не требует `Application.Current`, Dispatcher или ViewModel. GUI отображает прогресс через свой адаптер; CLI преобразует результаты в JSON и коды завершения.

При реализации выделить необходимые сервисы и модели в общую библиотеку, не переносить в неё окна и предзагрузку GUI. Подготовка структуры проектов — часть реализации; масштабный рефакторинг и смена .NET не являются целью. Начальный ориентир — текущий .NET Framework 4.7.2.

CLI не должен вызывать существующий GUI-bootstrap, получать конфиг с сервера, запускать автообновление или сохранять историю запуска GUI.

## 4. Контракт запуска и результатов

### Пути и конфигурация

- Поддержать `--config <path>` во всех командах, которым нужны правила.
- Без `--config` искать `config.js` рядом с CLI EXE, независимо от текущей рабочей директории.
- Явные относительные пути в аргументах разрешать относительно рабочей директории вызывающего процесса.
- В JSON возвращать абсолютные пути входа, фактически загруженного конфига и созданного выхода, а также хеш конфига для воспроизводимости.
- Не менять рабочую директорию процесса ради поиска конфигурации.
- При работе с новой формой использовать копию конфига выбранной фирмы, например `work\candidate.js`.
- Команды проверки не изменяют рабочий конфиг и другие конфиги фирм.

### Машиночитаемый вывод

Поддержать `--json`. В этом режиме stdout содержит ровно один JSON-документ, без баннеров, прогресса и сообщений `log()` из правил. Логи и прогресс направлять в stderr и при необходимости в явно выбранный файл.

Общий конверт результата:

```json
{
  "schemaVersion": 1,
  "command": "validate",
  "status": "failed",
  "data": {},
  "warnings": [],
  "errors": [
    {
      "code": "INVALID_NUMBER",
      "stage": "dbf-write",
      "form": "Форма 2.21А",
      "sourceRow": 18,
      "field": "SUMMA",
      "actual": "не число",
      "message": "Значение поля SUMMA не является числом"
    }
  ]
}
```

Это пример будущего формата. Зафиксировать итоговые поля и коды до реализации команд. Не сериализовать напрямую Jint, COM, DI-контейнер или словари с объектами `DocForm` в качестве ключей.

Для ошибки указывать этап, форму, исходную строку Excel, поле, ожидаемое и фактическое значение, когда это применимо. Позицию JS и стек добавлять, если Jint их предоставляет; не придумывать отсутствующие координаты. Отделять ошибку правила от штатного несовпадения формы.

Предлагаемые коды завершения:

| Код | Значение |
| --- | --- |
| 0 | Команда успешно выполнена, критерии проверки соблюдены |
| 1 | Правила или данные не прошли проверку, форма не найдена либо регрессия обнаружила отличие |
| 2 | Некорректные аргументы команды |
| 3 | Проблема среды, COM, файлового доступа или непредвиденная ошибка выполнения |

Точная причина определяется полем `errors[].code`. JSON для ожидаемых ошибок также должен быть корректным. Состояние «подходящих форм нет» в `match` представлять явно и возвращать код 1. Наличие нескольких совпадений отражать отдельным предупреждением с указанием выбранной формы; строгий режим может считать его ошибкой.

### Прочие условия

- У каждой команды есть `--help`; общая справка сообщает путь к `AGENTS.md` и версии приложения, JS API и JSON-схемы.
- Поддержать ограничение времени выполнения. Его реализация должна завершать зависшую операцию и освобождать принадлежащие ей ресурсы, а не только прекращать ожидание вызывающего кода.
- Диагностические сообщения и JSON сохраняют кириллицу при запуске из поддерживаемых версий PowerShell.
- Ошибки CLI не открывают `MessageBox` или другие диалоги.

## 5. Команды первой версии

### `doctor`

Проверяет версию приложения, доступность зависимостей и возможность создать и корректно закрыть собственный экземпляр Excel. Сообщает версию и разрядность там, где их можно надёжно определить, путь к документации и доступность временной директории.

Отсутствие конфига не должно мешать общей диагностике среды. Если передан `--config`, проверить его наличие. Загрузка и проверка самих правил относятся к `check-config`.

### `check-config --config candidate.js`

Работает без создания Excel. Загружает конфиг тем же JS-движком и с теми же базовыми функциями, что используются при конвертации.

Проверяет синтаксис, структуру `app.settings` и `app.forms`, наличие обязательных функций, параметры чтения, схему DBF, допустимость кодировки и положительный размер буфера. Для динамического `startY` учесть существующий сценарий с плавающим заголовком: окончательное значение проверяется после распознавания.

Выдаёт список форм и их схем. Дубли имён, подозрительные параметры и неподдерживаемые свойства должны получать понятную диагностику. Обязательные ошибки и предупреждения разделить с учётом совместимости существующих конфигов.

Эта команда не доказывает корректность `rules`, `write` и хуков на реальных данных. Выполнение конфигурационного JS ограничить по времени; «проверка синтаксиса» не должна незаметно превращаться в неограниченный запуск произвольного скрипта.

### `inspect file.xlsx --range A1:M30`

Открывает документ через тот же Excel-сервис, который используется конвертацией. Возвращает список листов, выбранный лист, адрес используемого диапазона и значения запрошенных ячеек с координатами.

Дать ограниченный результат по умолчанию и возможность запросить другой диапазон. Различать пустую ячейку, ошибку чтения и типизированное значение. Показать отдельно значение, которое увидят правила, и исходное значение, если они различаются. Формулы и отображаемый текст можно добавить как опциональные поля.

В первой версии конвертация сохраняет выбор первого листа. Если `inspect` позволяет выбрать другой лист, отчёт и справка должны явно сообщать, что текущая конвертация его не использует. Поддержку выбора листа в правилах не добавлять скрыто.

### `match file.xlsx --config candidate.js`

Выполняет распознавание без создания DBF. Показывает выбранную форму, все обнаруженные совпадения, результаты выполненных `assert`, координаты ячеек, ожидания, фактические значения и ошибки JS.

Различать проверки, которые выполнены, и проверки, пропущенные из-за `fastSearch` или явного выхода из JS-функции. Для получения расширенного отчёта предусмотреть `--all-forms`: он запускает отдельный диагностический поиск и явно сообщает, что режим поиска отличается от рабочего.

Обычный `match` должен воспроизводить фактический выбор формы при конвертации. Диагностический перебор не должен изменять сохранённый контекст выбранной формы.

### `validate file.xlsx --config candidate.js`

Выполняет весь рабочий цикл: распознавание, определение начала данных, `beforeWrite`, обработка строк, запись временного DBF, `afterWrite`, закрытие и чтение результата.

Проверка должна использовать ту же реализацию, что и `convert`, включая кодировку, типы, ограничения полей, обработку `null` и `stop()`. Предпросмотр первых строк не заменяет полного прохода и заключительного хука.

Результат включает выбранную форму, схему DBF, эффективный `startY`, число прочитанных, пропущенных и записанных строк, причину остановки и ограниченную выборку записей. При ошибке — исходную строку и этап. Пропуск строки считать только при фактическом выполнении `write`, возвратившем `null`, а не для всех строк после `stop()`.

Временный DBF проверять повторным чтением: заголовок, типы, количество записей, декодирование и значения. Это проверяет формат и преобразование, но само по себе не доказывает принятие файла коммерческой CRM.

Путь, рассчитанный `app.getOutputFilename`, показывать как планируемый, но не использовать для записи пробного результата рядом с исходником. Временные артефакты удалять после проверки; предусмотреть явное сохранение для разбора ошибок.

### `convert file.xlsx --config candidate.js --output result.dbf`

Использует тот же цикл, что `validate`, и публикует итоговый DBF только после успешного завершения хуков и проверок записи. При ошибке не оставляет по целевому пути частичный DBF, который выглядит готовым.

Если `--output` не указан, сохранить существующее вычисление имени через `app.getOutputFilename`. В CLI запретить перезапись существующего файла без явного `--overwrite`. При разрешённой перезаписи старый файл должен сохраняться до успешного создания нового.

Не менять одновременно привычную политику перезаписи GUI без отдельной оценки совместимости.

### `test --manifest TestData\cases.json --config candidate.js`

Запускает регрессионный набор из готовой поставки. Не требует MSTest, исходников и сборки. Возвращает результат по каждому сценарию и общий код завершения.

## 6. Семантика правил и совместимость

До изменения поведения составить проверяемое описание текущего JS API. В частности:

- `cell(y, x)`: начало координат, тип возвращаемого объекта, регистр `Value`, `Y`, `X`, поведение пустой ячейки и ошибки чтения.
- `findRange(startY, endY, startX, endX, expect)`: фактический порядок аргументов, включение границ и поведение единичного диапазона. Комментарии в конфиге сейчас указывают другой порядок.
- `assert`: поддержка строк и регулярных выражений, правила сравнения, влияние `fastSearch`.
- `line`: реальные типы значений и соответствие индекса номеру столбца. В текущем `GetRow` индекс 0 заполняется значением по умолчанию, а чтение последнего столбца требует проверки. Комментарий «индексация с 0» нельзя принять за достоверный контракт.
- `context`: область жизни, сохранение результатов распознавания выбранной формы и отсутствие влияния других форм и документов.
- `context.startY`: момент применения относительно `beforeWrite` и допустимые значения.
- `write`: объект записи, `null` для пропуска, `stop()` для остановки, ошибочные возвращаемые типы.
- Базовые функции: `match`, `matches`, `includes`, `translit`, `nospace`, `afterRegEx`, `log`, `error`; отдельно определить статус заглушки `test`.
- Именование результата: `app.getOutputFilename`, `file`, `dir`, `dirCount` и относительные пути.
- Числа, даты, локаль, ширина DBF в байтах, точность и поведение при обрезании строк.

Не обещать поддержку современного JavaScript целиком: описать проверенные возможности установленной версии Jint. Различать JS-регулярные выражения и строки с шаблонами, которые обрабатывает .NET Regex.

Отдельно проверить потенциальные дефекты: общий `context` при переборе форм, успешное распознавание без выполненных `assert`, границы блоков Excel, смещение номера исходной строки, чтение последнего столбца и расчёт границ `UsedRange` при начале диапазона не с A1.

Каждое подтверждённое исправление сопровождать содержательной регрессионной проверкой. Не исправлять индексацию и другие спорные места без оценки существующих JS-конфигов. Если совместимость сохранить нельзя, явно документировать изменение API и необходимую правку правила.

Для обрезания строк и преобразования данных в первой версии выдавать предупреждения. Предусмотреть строгий режим, превращающий конкретные виды потерь в ошибку. Не считать результат корректным только потому, что библиотека DBF не выбросила исключение.

## 7. Работа с Excel и освобождение ресурсов

- Создавать экземпляр Excel, принадлежащий текущей операции; открывать исходник без сохранения изменений и без обновления внешних связей, если это совместимо с используемыми форматами.
- Определить явную политику макросов, пересчёта формул и системных диалогов, чтобы CLI не зависел от ручного нажатия кнопок и пользовательских настроек Excel.
- Все COM-операции выполнять в согласованном потоке с корректной COM-инициализацией; для реализации ориентироваться на выделенный STA-поток.
- Гарантировать закрытие книги и освобождение COM-ссылок при успехе, исключении и отмене.
- Не завершать все процессы `EXCEL.EXE`: открытый пользователем Excel не принадлежит CLI.
- Если для надёжного тайм-аута нужен отдельный рабочий процесс, завершать только процесс и экземпляр Excel, принадлежность которых операции установлена явно.
- Отдельно проверить существующий CSV-конвертер, если он используется поддерживаемыми конфигами. CLI не должен наследовать его диалоги об ошибках.

## 8. Регрессионные данные

Начать с существующих `Example1.xlsx`, `Example2.xlsx`, `Example3-error.xlsx`, `Example4.xlsx`, `Example5.xls`, `Example6-js-error.xls`. Ожидаемый исход каждого примера сначала установить по данным и правилам; название файла не заменяет проверки.

Подготовить версионируемый `cases.json`. Для сценария хранить относительный путь к входу, ожидаемый исход, форму, число записей и несколько ожидаемых значений. Для ошибок — устойчивый код и этап; для финансовых итогов — точное правило сравнения с явно заданной допустимой погрешностью.

Сравнивать содержимое DBF с учётом типов и кодировки. Побайтовое сравнение использовать только там, где исключены изменяемые служебные поля, например дата создания в заголовке.

Добавить отрицательные сценарии: близкий неподходящий заголовок, отсутствие формы, ошибка числа, ошибка JS, сбой `afterWrite`, отсутствие ожидаемой итоговой строки. Проверить одиночную ячейку, последний столбец, границы буфера, плавающий заголовок, влияние порядка форм и повторную обработку документов.

Набор для фирмы должен проверять её собственный конфиг. Не объединять правила разных фирм ради тестирования. При необходимости общий набор запускается отдельно для каждого конфига со своими ожиданиями.

Исходники, утверждённые ожидания и эталоны хранить вне игнорируемого `bin`. Копировать их в поставку через настройки проекта. Случайно оставшиеся DBF из `bin\Debug` не включать в эталоны автоматически.

## 9. Документация в готовой поставке

Предлагаемая структура:

```text
ExcelToDbf.exe
ExcelToDbf.Cli.exe
config.js
AGENTS.md
docs/
  cli.md
  rules-api.md
  dbf-format.md
  examples/
TestData/
  cases.json
  ...проверенные примеры...
DLL/
  ...зависимости...
```

`AGENTS.md` — короткая инструкция для модели: назначение программы, обязательное чтение справочника, выбор фирмы и конфига, создание кандидата, команды проверки и критерии готовности. Документ должен работать без ссылок на исходники и знания структуры C#.

В `rules-api.md` описать жизненный цикл, структуру настроек и форм, все поддерживаемые функции, типы, координаты, регулярные выражения, ошибки и рабочие примеры. В `dbf-format.md` — фактический вариант DBF, кодировку, поля, ограничения и преобразования, подтверждённые реализацией и проверенными файлами.

В `cli.md` привести команды PowerShell, JSON-контракты, коды завершения, правила путей и сохранения артефактов. Документацию связывать относительными ссылками внутри поставки.

Копирование документации настроить в проектах сборки; проверить её наличие и ссылки в Debug и Release. Сам план из `docs\plans` не обязан попадать в поставку: это документ разработки.

`AGENTS.md` не всегда читается агентами автоматически. Поэтому `--help` должен явно указывать на него; начальная инструкция пользователю также должна содержать предложение открыть этот файл.

## 10. Обычный сценарий модели

После реализации из директории поставки модель выполняет примерно следующую последовательность:

```powershell
.\ExcelToDbf.Cli.exe doctor --json
New-Item -ItemType Directory -Path .\work -Force
Copy-Item -LiteralPath .\config.js -Destination .\work\candidate.js
.\ExcelToDbf.Cli.exe inspect .\incoming\new.xlsx --range A1:M30 --json
# Модель дописывает форму в work\candidate.js по справочнику rules-api.md.
.\ExcelToDbf.Cli.exe check-config --config .\work\candidate.js --json
.\ExcelToDbf.Cli.exe match .\incoming\new.xlsx --config .\work\candidate.js --json
.\ExcelToDbf.Cli.exe validate .\incoming\new.xlsx --config .\work\candidate.js --json
.\ExcelToDbf.Cli.exe test --manifest .\TestData\cases.json --config .\work\candidate.js --json
.\ExcelToDbf.Cli.exe convert .\incoming\new.xlsx --config .\work\candidate.js --output .\work\result.dbf --json
```

После каждой команды проверять `$LASTEXITCODE` и JSON, при ошибке исправлять правило и повторять необходимые проверки. Этот пример показывает последовательность, а не готовый скрипт с обработкой ошибок.

Итог работы модели — подготовленный конфиг конкретной фирмы, отчёт о проверках и при необходимости DBF в явно выбранной директории. Замена рабочего `config.js` — отдельный явный шаг по запросу пользователя, с сохранением предыдущей версии; команды проверки её не выполняют.

## 11. Порядок реализации

| Этап | Работа | Критерий завершения |
| --- | --- | --- |
| 1. Базовое поведение | Проверить примеры, зафиксировать текущий JS API и ожидаемые результаты; отделить найденные дефекты от особенностей совместимости | Есть воспроизводимые исходные сценарии и список подтверждённых изменений |
| 2. Общий запуск | Выделить механизм обработки, параметры, DTO результатов и адаптеры прогресса; убрать зависимость обработки от окон | GUI продолжает конвертировать; механизм вызывается без GUI |
| 3. Основа CLI | Добавить консольный проект, пути, JSON, коды завершения, обработку ошибок, `doctor` и `check-config` | Команды работают из собранной поставки и из другой рабочей директории |
| 4. Исследование файлов | Реализовать `inspect` и `match`, сохранение выбранного контекста и расширенный диагностический поиск | Модель видит данные и причины выбора либо отклонения формы |
| 5. Полная проверка | Реализовать `validate`, `convert`, временный вывод, повторное чтение DBF, диагностику потерь и тайм-аут | Проверка и конвертация используют один цикл; ошибочный файл не публикуется |
| 6. Регрессии | Добавить manifest и команду `test`, утвердить ожидания, проверить известные дефекты и совместимость | Добавление новой формы можно проверить без исходников |
| 7. Поставка | Написать `AGENTS.md` и справочники, настроить копирование и зависимости, обновить вводные документы репозитория | Полный сценарий воспроизводится из чистой поставки |

Документацию и проверки уточнять вместе с реализацией, не откладывая фиксацию контракта до последнего этапа.

## 12. Итоговая приёмка

- Модель с доступом только к поставке и Excel может добавить форму в копию конфига и проверить её командами из документации.
- Не нужны C#-рефлексия, загрузка сборок в PowerShell, Visual Studio и управление GUI.
- Проверки проходят на Windows с Excel при путях с пробелами и кириллицей, включая запуск из другой рабочей директории.
- `check-config` не создаёт Excel; остальные команды закрывают принадлежащие им ресурсы после успеха и ошибок.
- Проверены отсутствие формы, несколько совпадений, ошибка JS, недопустимые значения DBF, ошибка заключительного хука, тайм-аут и конфликт выходного пути.
- Номера строк в диагностике соответствуют исходному Excel, а не номеру записи DBF.
- `validate` проверяет весь документ и фактическую запись DBF; ограничение объёма JSON не ограничивает объём проверки.
- Регрессионный набор проверяет старые формы, отрицательные примеры и отсутствие влияния контекста между формами и документами.
- GUI и CLI используют одинаковую семантику преобразования; различия политики поиска, путей или перезаписи явно документированы.
- Debug/Release-поставка содержит CLI, зависимости, инструкции и утверждённые тестовые материалы. Post-build не ломает запуск CLI.
- Сборка и обновление поставки не теряют локальные конфиги фирм. Учесть, что `PreserveNewest` сам по себе не обеспечивает сохранность рабочих правок при копировании более нового исходного конфига.
- Тестовое редактирование не заменяет рабочий конфиг. Для выпуска новой версии конфигурации сохраняются предыдущий файл и отчёт проверки.

## 13. Что остаётся за рамками

- Перевод старых XML-конфигов фирм на JS.
- Работа без Excel, замена OLE и поддержка Linux/macOS.
- Встроенная LLM, сетевой API, MCP-сервер и автоматическое обращение к внешним моделям.
- Переписывание GUI и переход на другую платформу .NET.
- Объединение конфигов фирм, серверное обновление правил и новая система управления конфигурациями.
- Полноценный отладчик JS и редактор правил внутри приложения.

Открытые технические детали — окончательная структура общей библиотеки, поддерживаемые версии PowerShell и формат manifest — уточняются при реализации и проверке среды. Они не требуют менять выбранный основной сценарий: готовая поставка, локальный JS-конфиг и CLI-проверки через установленный Excel.
